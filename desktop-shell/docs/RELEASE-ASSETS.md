# Release 里三个文件各自的作用

每个 Release 都有三个文件。只有 `.exe` 是给人点的，另外两个是**给程序读的**。

```
Endaxis-Setup-1.0.8-x64.exe           116.8 MB   安装程序（人点这个）
Endaxis-Setup-1.0.8-x64.exe.blockmap    0.12 MB   差分下载索引
latest.yml                              0.4 KB    版本清单
```

三者缺一不可。下面分别说明，以及**缺了会怎样**。

---

## `latest.yml` — 版本清单（最重要）

**作用：告诉客户端"现在最新是什么版本、去哪儿下、下载下来的东西对不对"。**

内容长这样：

```yaml
version: 1.0.8
files:
  - url: Endaxis-Setup-1.0.8-x64.exe
    sha512: 2R16y0WnS4vRkXypC0YH1WnJZpOchi/CR4Yz6Hh0gCF...
    size: 122486178
path: Endaxis-Setup-1.0.8-x64.exe
sha512: 2R16y0WnS4vRkXypC0YH1WnJZpOchi/CR4Yz6Hh0gCF...
releaseDate: '2026-10-12T20:04:53.740Z'
```

客户端启动约 8 秒后做的第一件事就是**下这个文件**，然后：

1. 把 `version`（1.0.8）和本机版本比较 —— 这就是"决定要不要提示更新"的**唯一依据**；
2. 确认新就下载 `url` 指向的安装包；
3. 下完用 `sha512` 校验，**对不上就丢弃并报错**，不会去执行一个损坏或被替换过的安装包。

`sha512` 这一条是这个文件最重要的价值：**它是"下载的包确实是发布者上传的那一份"的
唯一凭据**。GitHub 只保证传输完整，不保证内容是你发的。

> **缺了会怎样**：客户端根本不知道有新版本存在，更新功能**完全失效**且没有任何提示。
> 这是三个文件里最不能少的。

> **为什么 `version` 必须递增**：客户端只做"新版本号是否更大"的比较。
> 如果新 Release 的版本号不大于本机版本，客户端会认为"已是最新"，
> 哪怕文件其实换了内容。

---

## `.blockmap` — 差分下载索引

**作用：让客户端只下载"变化了的那部分"，而不是每次重下整个 116 MB。**

它把安装包切成很多小块并记录每块的哈希。客户端已经装过旧版本时，
本机缓存里还有旧安装包，于是可以对比新旧 blockmap：

```
旧包块: [A][B][C][D][E]
新包块: [A][B][C'][D][E]
                    ↑ 只有这块变了 → 只下载这块
```

改一行前端代码通常只影响压缩包里的少数块，于是更新只需下载几 MB 甚至几百 KB。
实测本项目一次小改动走差分下载约 **117 MB → 数 MB 级别**。

> **缺了会怎样**：**功能不受影响**，更新照常工作，只是每次都要完整下载 116 MB。
> 对网络差的用户体感差别很大，但不会导致更新失败。
>
> 它属于"少了会变慢、不会坏"的那一类 —— 与 `latest.yml` 完全不同。

---

## 为什么不能只传 `.exe`

- **只传 exe**：客户端不知道有新版本（没有清单可读）→ 更新功能失效。
- **只传 exe + blockmap**：同样失效，仍然没有清单。
- **传 exe + yml，漏 blockmap**：更新可用，但每次全量下载。
- **三个都传但 yml 里的 sha512 与 exe 不一致**：客户端下载后校验失败，
  更新报错并中止（**这反而是保护**：宁可更新失败，也不执行来路不明的安装包）。

---

## 校验怎么做（发布流程里已自动做）

发布脚本上传完会跑一遍**匿名**验收，模拟客户端的行为：

```powershell
node --use-env-proxy tools/verify-release.mjs <owner> <repo> <version>
```

它会：

1. 不带任何凭据下载 `latest.yml`（客户端就是匿名的，带凭据的成功不算数）；
2. 检查 `version` 是否等于刚发布的版本；
3. **用线上清单里的 sha512 与本地安装包实算值比对** —— 确认上传上去的就是这一份字节；
4. 确认安装包可下载，且远端大小与清单一致；
5. 确认 `.blockmap` 存在（缺了只提示，不算失败）。

两个实测踩过的坑，脚本里都做了处理：

- **CDN 按文件名缓存**：重复发布同一版本时，无参请求可能返回**上一份**文件，
  于是误报"大小与清单不符"。所以请求都带随机查询参数绕过缓存。
- **本地清单与线上清单同批才算数**：比对 `releaseDate`，避免拿旧构建的清单
  验新上传的文件（会出现"看起来都对"的假通过）。
